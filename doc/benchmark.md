# 性能基准

可复现驱动位于 [`benchmark/`](../benchmark/README.md)。GitHub Actions 会在每次推送到主分支时运行两端驱动，并将
实时 HTML 与原始 CSV 发布到 Pages；本文件保留固定硬件上的分析结果，不提交 CI 生成数据。

## 结论

2026-07-23 的本机微基准显示，修复逐字节遍历全部模式的错误、移植连续 NFA/DFA/字节类，并专门化首字节预过滤后，
仓颉端不再存在数千倍或 13 倍的自动机算法差距：

- 稀疏字节搜索为 `0.0986 ms`，Rust 关闭 SIMD 预过滤后为 `0.214 ms`，仓颉端反而约快 `2.17x`。
- Rust 默认启用 `memchr`/SIMD 预过滤时为 `0.0368 ms`，仓颉端约慢 `2.68x`。
- 高重叠搜索为 `0.220 ms`，Rust 为 `0.0880 ms`，约慢 `2.50x`。
- 构建 1,000 个模式约慢 `3.59x`；低层视图所需的 Trie 直接边也计入构建与内存成本。

因此稀疏搜索的剩余最大差距来自平台向量化预过滤，而不是没有正确实现 Aho-Corasick。仓颉标准库目前没有与 `memchr`
对应的公开字节搜索入口；项目坚持纯仓颉实现，不通过 FFI 调用 libc。高重叠场景还受结果对象、容器和语言运行时成本影响，
其 `2.50x` 差距与纯字节循环的 `3.02x` 基线处于同一量级。

## 环境

- CPU：Intel Core i5-12450H，8 核 12 线程
- 系统：Linux x86_64
- Rust：`rustc 1.89.0`，`opt-level = 2`
- Rust 上游：本地提交 `c821786`（crate 版本 1.1.4）
- 仓颉：Cangjie 1.1.3 STS，`cjnative`，`-O2`
- 日期：2026-07-23

## 方法

每项先预热 3 次，再运行 5 个样本并取中位数；完整驱动独立运行 3 次，表中使用三轮中位数的中位数。两端都完整收集
结果并计算校验和。

- 构建：`needle-0` 至 `needle-999`，共 1,000 个模式。
- 稀疏搜索：113,292 字节、50 次命中。
- 高重叠：模式 `a` 至 `aaaaaaaa`，在 1,024 个 `a` 中产生 8,164 个结果。
- 校验和：稀疏 `5,506,951`，高重叠 `8,388,468`，两端一致。

## 结果

| 操作 | Rust | aho4cj 1.1.3 | 仓颉/Rust |
|---|---:|---:|---:|
| 构建 1,000 个模式 | 0.620 ms | 2.226 ms | 3.59x |
| 稀疏字符串搜索 | 0.0374 ms | 0.132 ms | 3.52x |
| 稀疏字节搜索 | 0.0368 ms | 0.0986 ms | 2.68x |
| Rust 连续 NFA，关闭预过滤 | 0.214 ms | 0.0986 ms | 0.46x |
| 纯字节遍历 | 0.0129 ms | 0.0390 ms | 3.02x |
| 高重叠搜索并收集 | 0.0880 ms | 0.220 ms | 2.50x |

字符串搜索比字节搜索多约 `0.033 ms`，主要是 UTF-8 字节数组构造。已持有 `Array<Byte>` 的调用方应优先使用 Bytes API。

## 已修复的性能问题

早期实现每读取一个输入字节都会检查最多 1,000 个模式是否为空，113,292 字节输入因此执行约 1.13 亿次检查；同时还会
收集、排序和复制所有候选。当前实现构建时预计算空模式编号，标准和左最搜索均按需产出结果，搜索热路径使用冻结后的连续
数组。批量重叠 API 保留专用扫描内核，避免每个结果一次闭包迭代调度。首字节预过滤进一步针对 1、2、3 个候选分别
生成热路径，并把最常见的单候选扫描按 8 字节展开，使稀疏字节搜索从 `0.212 ms` 降到 `0.0986 ms`。
